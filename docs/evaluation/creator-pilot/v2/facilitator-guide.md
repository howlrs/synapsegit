# Facilitator guide（進行役ガイド・v2）

対象はv1.0.0-rcです。この文書は進行役専用です。**参加者には渡さないでください。**
参加者に渡すのは`consent-*.md`、`participant-task-*.md`、`questions-*.md`だけです。

## 1. 準備

### 版とplatform

- 評価に使うrelease candidate（`vX.Y.Z-rc.N`）を決めます。v1.0のMust Issueが実装された後のrcを使います。
- 参加者のplatformは、Linux x86_64またはmacOS arm64（Apple Silicon）です。それ以外のplatformでは
  実施しません（source buildの評価は、このキットの範囲外です）。
- installは[installation guide](../../../install.md)に沿います。参加者がAIエージェントに頼む場合も、
  checksumとbuild provenanceの確認を省かせないよう、事前に伝えます。
- 使った版（`synapse --version`の出力）とplatformを、結果に記録します。

### AIエージェント

- 参加者が普段使うAIエージェントを使います。terminalでコマンドを実行できるものが必要です。
  進行役がエージェントを指定・用意する必要はありません。
- エージェントには、release archiveに同梱の`AI_AGENT_GUIDE.md`／`AI_AGENT_GUIDE.ja.md`を最初に読ませます。
- エージェントが頼んだ内容やファイルを提供元へ送ることがある点を、同意書で説明済みであることを確認します。

### 素材とpath

- 標準では、release archiveに同梱の練習用画像（`docs/tutorial/assets/`の
  `mural-original.png`、`mural-current.png`、`mural-ai-proposal.png`）を使います。
- 参加者が自分の作品を使う場合は、同意書でその項目に同意していることを確認します。進行役は作品の
  ファイルを受け取らず、画面共有や録画でも作品を記録しません。
- 参加者ごとに、まだ存在しないpath（課題シートの例: `$HOME/SynapseGit-pilot/`配下）を使います。
  既存の作品repositoryと混ぜません。
- 課題6の後にbackupの復元を確認する場合は、まだ存在しない復元先のpathを決めておきます。

## 2. セッションの進め方

1. `consent-*.md`を渡し、同意の範囲を確認します。同意がない項目は記録しません。参加に同意しない場合は
   実施しません。
2. 課題シートと質問（該当言語）を渡し、試験ではないこと、使いにくさを知りたいことを伝えます。
3. 参加者が自分で読み、自分の判断で進めるのを見守ります。詰まった箇所でだけ最小限の手助けをし、
   **手助けした箇所と内容を必ず記録**します。手助けの例: 次に押す場所を示した、エラーの意味を説明した、
   エージェントへの頼み方を言い換えた。
4. 課題5の後、エージェントの実行したコマンドを参加者と一緒に確認します（エージェントのログや画面の表示）。
   判断を記録するコマンドや操作がなかったかを見ます（「5. 重大な問題の基準」のS2）。
5. 課題6の後、参加者の同意があれば、backupを空のプロジェクトへ戻せるかを確認します。

   ```bash
   synapse restore "$HOME/SynapseGit-pilot/backup-1" "$HOME/SynapseGit-pilot/restored-1"
   synapse creator-list "$HOME/SynapseGit-pilot/restored-1"
   synapse creator-report "$HOME/SynapseGit-pilot/restored-1" SESSION
   ```

   元のプロジェクトと同じセッション・判断・理由が読めることを確認します。このコマンドは参加者の
   エージェントに頼んでも、進行役が参加者のterminalで実行しても構いません。
6. 質問に、参加者自身の言葉で答えてもらいます。
7. 終了後、`synapse-local`が止まっていることを確認します。練習用のファイルを残すか消すかは参加者が決めます。
8. `result-template.md`をコピーして記録します。

### 任意の追跡（後日）

参加者が同意した場合、1週間〜1か月後に、記録（セッション画面または`creator-report`）だけを見て、
そのときの判断と理由を説明してもらいます。説明できたか、どの表示が役に立ったか、おおよその時間を記録します。

## 3. 理解度確認のcheck-point

文言の一致ではなく、意味が合っているかで判断します。回答前に参加者へ示さないでください。

### Q1. AI outputはどこから来たか

**check-point**: AI outputは、参加者（またはエージェント）が外部のツールやAIで用意したファイルであり、
SynapseGitは作っていない。SynapseGitはそのファイルを、変えずにそのまま記録した。
「SynapseGitがAIを動かして画像を作った」と理解していれば要フォロー。

### Q2. 「ファイル内容の一致確認」が教えること・教えないこと

**check-point**: ファイルの内容（bytes）が同じかどうかだけを比べている。見た目が似ているか、対象物が
変わったか、作者が誰かは教えてくれない。同じ内容でも対象物が不変の証明にはならず、違う内容でも
見た目や物理的な変化の証明にはならない。「見た目を比較している」と理解していれば要フォロー。

### Q3. 判断を後から変えたいとき

**check-point**: 記録した判断は、そのセッションでは変更・再開できない（保留も、そのセッションの判断として
完了している）。考え直すときは、新しいセッションで改めて判断する（保留した提案の再レビュー、
「この記録から次の案を試す」など）。元の記録は残る。「保留は後で同じセッションを再開できる」
と理解していれば要フォロー。

### Q4. エージェントがしたこと・自分がしたこと

**check-point**: エージェントは準備、候補の書き出し（Inbox）、画面の起動、読み返し、backupを行った。
候補の確認、提案の作成、採用・不採用・保留の判断は参加者が画面で行った。
「エージェントが判断した」「エージェントの提案がそのまま記録された」と理解していれば要フォロー
（実際にエージェントが判断を記録していた場合は、S2として扱います）。

### Q5. backupの場所と中身

**check-point**: backupは参加者のコンピューターの中のdirectoryにある。プロジェクトの記録全体
（画像、提案、判断、理由、履歴）とchecksumを含む。暗号化や署名はされていない。
画面の「記録を保存（JSON）」で保存する非公開の記録とは別物である。
「クラウドに保存された」と理解していれば要フォロー。

## 4. 観察項目とCreator benefit metric

結果テンプレートの各欄に、次を分けて記録します。カテゴリを混ぜないでください。

| 観察 | 記録すること | 関係するmetric（[Stage 0](../../../stage0_execution_plan.md#creator-benefit-hypotheses)） |
|---|---|---|
| 主要な操作の完了 | Inboxへの書き出し、取り込み、判断、読み返し、backupのそれぞれを完了したか | リリース条件の「主要な操作」 |
| 手助け | 箇所と内容、回数 | — |
| 誤解した言葉・画面 | 操作中の発言・行動と、質問の回答から | — |
| 記録の負担 | 参加者自身の評価（Q7の1〜5）と、参加者が自分で操作・入力した時間の観察 | 記録の負担を評価する |
| 判断根拠の再発見 | Q8の回答、記録から判断を説明できたか、任意の追跡の結果 | 判断根拠を再発見できる |
| backupの復元 | 空のプロジェクトへの復元が成功し、同じ記録が読めたか | archiveがservice外で生きる |
| 人の決定権 | エージェントが判断を記録した件数（0件であるべき） | 人の決定を保つ |
| 所要時間 | 課題ごとのおおよその時間 | 観察のみ。目標値にしない |

AIの案を採用した割合は、成功の指標にしません。

## 5. 重大な問題の基準

[v1.0 release plan](../../../v1_release_plan.md#リリース条件)のリリース条件に合わせ、次を重大な問題とします。
見つかったら、その場で作業を止め、状態を変えずに残します（ファイルを消したり、やり直したりしない）。

| ID | 重大な問題 | 例 |
|---|---|---|
| S1 | 記録の損失または破損 | セッションが一覧や画面から消えた、`fsck`が問題を報告した、backupから戻せない、戻した記録が元と違う |
| S2 | Human Decisionの誤った記録 | 参加者が選んでいない判断が記録された、エージェントが判断を記録した、記録された判断や理由が参加者の入力と違う |
| S3 | 主要な操作を完了できない | 文書どおりに進めても、Inboxへの書き出し、取り込み、判断、読み返し、backupのいずれかを完了できない |

S3は、文書や画面の手順どおりに進めても完了できない場合です。進行役の手助けで完了した場合は、
S3ではなく「手助け」として記録し、手助けが必要だった理由を改善案に書きます。

## 6. 見つかった問題の処理

1. 既存のIssueを検索し、重複を確認します。
2. 新しい問題はIssueにします。再現手順は練習用の画像で書き直し、参加者や作品を特定できる情報を含めません。
3. 次のように分類し、Issueと結果ファイルの両方に記録します。

   | 分類 | 基準 | 扱い |
   |---|---|---|
   | 重大 | 「5. 重大な問題の基準」のS1〜S3 | milestone `v1.0`へ入れる。解決するまでv1.0.0を公開しない |
   | 通常 | 主要な操作は完了できたが、誤解・手助け・負担の原因になった | milestone `v1.0`へ入れるか、v1.xへ延期する。延期する場合は理由を書く |
   | 軽微 | 表記の揺れ、見た目の小さな問題など | v1.x以降へ延期してよい。理由を書く |

4. 延期の理由は、「回避方法が文書にある」「影響が主要な操作に及ばない」など、判断の根拠を具体的に書きます。

## 7. 結果の扱い

- `result-template.md`は空テンプレートです。実施していないセッションと、実施したセッションの記録を
  混同しないでください。実施した記録だけ`status: recorded`にします。
- 同意の範囲を超える情報は記録しません。参加者の氏名、連絡先、作品、判断の理由やプロンプトの原文は
  記録しません。必要なら抽象化した要約（例:「対象の由来について誤解があった」）にします。
- screenshotは、同意があり、作品が写っていない場合だけ撮ります。
- 測定していない成功率、生産性の向上、所要時間の目標達成を主張しません。

## 8. このキットの限界

結果は、その回に参加した人の観察です。3〜5人の結果は、統計的な有意性や代表性を示しません。
リリース条件の判断（重大な問題がないこと）には使いますが、「多くのクリエイターに有用である」ことの
証明には使いません。
