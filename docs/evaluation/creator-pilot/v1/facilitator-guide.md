# Facilitator guide（進行役ガイド）

対象はv0.9.0です。この文書は進行役（facilitator）専用です。**参加者には渡さないでください。**
参加者に渡すのは`participant-task-ja.md`／`participant-task-en.md`と
`comprehension-questions-ja.md`／`comprehension-questions-en.md`だけです。

## 1. 準備

- v0.9.0の`synapse`／`synapse-local`／`synapse-present`をinstallします
  ([Installation guide](../../../install.md))。cargoでのsource buildでも構いません。
- 練習用repositoryを用意します。参加者本人の実際の作品・実名を使う場合は、事前に本人の同意を
  取り、公開文書には決して実名・実作品・private rationaleをそのまま転記しないでください
  （詳しくは「5. 結果の扱い」）。
- 参加者に渡す前に、その回で使うAI output画像を進行役が用意しておきます
  （SynapseGitはモデルを呼び出しません。用意する画像は進行役の責任です）。
- 参加者の言語（日本語／英語）に応じて、`participant-task-*.md`と
  `comprehension-questions-*.md`のどちらかを選び、対応する理解度確認質問を用意します。
- 英語話者の参加者には、画面が日本語のみである旨を事前に伝え、必要に応じて読み上げ・翻訳の
  補助を進行役が行う想定でスケジュールを組みます。
- 参加者にCLIとブラウザUIのどちらの経路を課題1で使ってもらうか、事前に決めます
  （両方比べたい場合は、課題4の任意セッションで別経路を試してもらう方法もあります）。
- ブラウザUIでAdopt／Reject／Deferを確定する際は、ブラウザ標準の確認ポップアップ
  （`確認`／`キャンセル`）が表示されます。確認ダイアログが表示され、参加者が内容を
  読んでから選べることを事前に確認してください。
- 課題3b（公開用文章の下見）のために、CLI経路を選ぶ場合は、
  export先に使うまだ存在しない空ディレクトリを一つ用意しておきます
  （`synapse-present export`は既存pathへ書き出せません）。ブラウザ経路では
  プロジェクト画面の「公開用の制作ノートを作る」を開くだけで追加準備は不要です。

### releaseと画像だけで準備する場合

v0.9.0のbinary archiveには練習画像は含まれていません。以下のtag固定画像を保存し、
参加者へ3つのローカルpathを渡します。source checkoutがある場合は同名の
`docs/tutorial/assets/`内の画像を使えます。

- [Original: mural-original.png](https://raw.githubusercontent.com/howlrs/synapsegit/v0.9.0/docs/tutorial/assets/mural-original.png)
- [Current: mural-current.png](https://raw.githubusercontent.com/howlrs/synapsegit/v0.9.0/docs/tutorial/assets/mural-current.png)
- [AI output: mural-ai-proposal.png](https://raw.githubusercontent.com/howlrs/synapsegit/v0.9.0/docs/tutorial/assets/mural-ai-proposal.png)

既存の作品repositoryとは別に、まだ存在しないpathで練習repositoryを初期化します。
次の`REPO`をそのpathに置き換えます。ブラウザ経路では続けてserverを起動し、
表示されたURLを開いて`mural`プロジェクトへ進みます。CLI経路なら2行目は不要です。

```bash
synapse init REPO
synapse-local --project mural=REPO --port 0
```

参加者ごとに新しいrepositoryを用意し、終了後はserverを停止します。課題3bの`OUT`も
既存pathを使わず別の未作成pathを指定します。実際に使ったbinary versionと経路は
結果templateへ記録してください。

## 2. セッション中の進め方

1. 課題シートと理解度確認質問（該当言語）を渡し、目的（試験ではないこと、使いにくさを
   知りたいこと）を口頭で伝えます。
2. 参加者が`participant-task-*.md`の手順を自分で読み、自分の判断で進めるのを見守ります。
   詰まった箇所でだけ最小限の補助をし、**補助した内容と箇所を必ず記録**します。
3. 理解度確認質問に、参加者自身の言葉で回答してもらいます。回答中に画面や文書を見返すのは
   構いません（暗記テストではありません）。
4. セッション終了後、`result-template.md`をコピーして記録します。

## 3. 理解度確認の質問と check-point（期待される理解）

参加者向けの質問文には回答を書きません。ここに書く check-point は、参加者の回答が
「記録の意味を正しく理解しているか」を進行役が判断するための目安です。文言の一致では
なく、意味が合っているかで判断してください。

質問文は中立的なopen-ended表現にしてあり、回答を誘導する言い回し（例:「〜だと思いますか」の
yes/no形式）は使っていません。回答は自由記述で受け取り、次のcheck-pointと意味が合っているか
だけで判断してください。

### Q1. 3枚目の画像（AI output）はどこから来たか

**check-point**: 参加者が「AI outputはSynapseGit自身が生成したのではなく、外部（今回は
進行役）が用意して渡したファイルである」という趣旨を理解していること。SynapseGitが
モデルを呼び出して画像を作った、と誤解していれば要フォロー。

### Q2. `byte_identity`は何を教えてくれるか

**check-point**: 参加者が「`byte_identity`はファイルのbytesが一致するかどうかだけを
見ており、画像の見た目・pixelの類似性・物理的な変化・作者性は教えてくれない」という
趣旨を理解していること。「見た目が似ているかを判定している」という誤解が残っていれば
要フォロー。参加者が「教えてくれないこと」として見た目・pixel・物理的変化・作者性の
いずれかに自分で言及できていれば合致とみなします。

### Q3. Adopt時とDefer時で記録される内容の違い

**check-point**: 参加者が「どちらもそのセッションの判断として完了し、Adoptは`selected=true`
でAI outputが選ばれた状態、Deferは`selected=false`でCurrent（base）が維持されたまま
『保留』が記録される」という趣旨を理解していること。「Deferは後で再開できる一時保存」
という誤解が残っていれば要フォロー。

### Q4. rationaleはどこで読み返せ、誰が見られるか（課題3bを踏まえて）

**check-point**: 参加者が「課題3bで開いた公開用の制作ノート画面は、自分の判断理由
（rationale）を含まない空欄から始まる」こと、「`--rationale`や画面のprivate rationaleは
保存され、`creator-report`や完了したセッション画面（自分・同じprocessを使える人）からは
読み返せるが、`synapse-present`が作る公開bundleには自動転記されない」こと、
「公開用の文章（presentation sidecar／`presentation.toml`）は別に、自分で空欄から
入力・確認して作る必要がある」という趣旨を理解していること。「入力した理由がそのまま
外部公開される」という誤解が残っていれば要フォロー。
回答を受け取った後の説明には[公開用の制作ノート](../../../presentation_sidecar.md)と
[CLI reference](../../../cli_reference.md)を使えます。回答前に参加者へ示さないでください。

## 4. 観察項目（facilitator observation items）

セッションごとに`result-template.md`へ次を分けて記録してください。カテゴリを混ぜないことが
重要です。

- **完了／中断**: 課題1〜3（import→比較→判断→読み返し）と課題3b（公開用文章の下見）を完了したか、
  途中で中断したか。中断した場合はどの課題番号で、何が理由か。
- **補助が必要だった箇所**: 進行役が説明・操作を代行・助言した箇所と、その内容。
- **誤解していた文言**: 参加者が画面や文書の言葉をどう読み違えたか（例: 「AI」という語を
  見てモデル実行だと思った、など）。理解度確認質問への回答だけでなく、操作中の発言・
  行動からも拾います。
- **役に立った記録**: `creator-report`の出力、画面の確認画面、troubleshooting節など、
  参加者が「助かった」「分かりやすかった」と述べた・様子が見えた箇所。
- **負担に感じた操作**: 手順が長い、入力が面倒、画面遷移が分かりにくい等、参加者が
  負担を感じた操作。
- **改善案**: 参加者・進行役どちらからでも出た、文書やUIへの改善案。
- **所要時間**: 各課題にかかったおおよその時間。**これは観察であり、宣伝・目標値と
  混同しないでください。** 「◯分で完了できる」という主張の根拠にはしないでください。

## 5. 結果の扱い

- `result-template.md`は空テンプレートです。**実施していないセッションのテンプレートを
  埋めた記録と、実際に測定したセッションの記録を混同しないでください。** 未実施のテンプレート
  行は空欄のまま残し、「実施済み」と誤読されない形で保存してください。
  （空テンプレートそのものは`not_run`のマーカーを持つファイルとして扱います。)
- 参加者から記録の公開・共有について明示的な同意を得てから、必要な情報だけを記録します。
  同意がない場合、または同意の範囲を超える場合は記録しません。
- 公開する結果（issue、社内共有資料等）には、参加者の実名、実在の作品、private rationale
  の原文をそのまま転記しないでください。必要なら抽象化した要約（例:「対象の由来について
  誤解があった」）に置き換えます。
- 測定していない成功率・生産性向上・所要時間の目標達成を主張しないでください。観察した
  範囲でのみ記述します。
- 個人情報（氏名・メールアドレス・機密情報）は必要最小限にとどめ、公開文書へは記録しません。

## 6. このキット自体の限界

このキットで得られる結果は、その回に参加した1名（またはそのセッション）の観察に
とどまります。統計的な有意性、代表性、成功率を主張する設計にはなっていません。
複数回の実施結果を蓄積した上で、[Project status](../../../project_status.md#次の優先順位)の
「実利用者によるcreator benefit評価」の完了可否を別途判断してください。
